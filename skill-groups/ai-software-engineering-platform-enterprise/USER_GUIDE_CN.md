# 中文使用手册

## 一、轻量路由与初始化

```text
@AI工程轻量路由
```

会话第一条助手输出先显示中文轻量路由名称。解释、状态查询或不要求项目动作的简单诊断直接回答，不运行路由脚本；普通项目已有证据时一次守门，证据不足时最多一次检查加一次守门；只有多会话、合并、发布和长链路任务进入完整治理。每阶段最多两个活跃原子 Skill，路由本身不计入额度。

实际原子 Skill 回执来自完整读取后的加载遥测，不是“可能会用”的路由候选。请求同时包含“增强、审核、推送”时，先完成增强阶段，再 Checkpoint、重路由到审核，最后在用户已授权时进入推送；末尾动作不会覆盖当前工作。

自动模式不会要求每个项目都维护 `.ai`：没有 `.ai` 时直接以最新用户请求和当前 Git 无状态轻量推进。只有来源指纹与当前仓库一致的 `.ai` 才能恢复 Task、路由和既有 PASS；缺少可信指纹、仓库身份冲突或历史分叉时旧状态自动隔离，普通设计、实现、审核和测试继续，但禁止恢复旧任务、创建多会话/Worktree、合并或发布。用户无需手动选择 Skill，也无需手工清理旧 `.ai` 才能继续普通工作。

从空目录开始时先进入 `@0→1需求融合与选型`，生成：

```text
.ai/requirements/ledger.json
.ai/context/greenfield.json
REQUIREMENTS.md
```

新增需求按 `REQ-001` 等稳定ID增量合并；旧版本进入revision history，冲突和未知项必须显式保留。平台、架构、部署、数据、安全或核心技术栈变化会自动生成决策 Checkpoint，记录候选、证据、风险、回退和选择后继续正式脚手架，不弹出审批。

已有部分源码、半成品或二次开发项目先由 `@项目智能初始化` 识别真实技术与版本，再进入 `@存量源码需求对账`，生成：

```text
.ai/requirements/source-baseline.json
.ai/requirements/ledger.json
.ai/requirements/reconciliation.json
.ai/context/requirement-reconciliation.json
REQUIREMENT_DELTA.md
```

现有能力使用 `CAP-001` 等稳定ID并附代码或测试证据；自定义需求使用 `REQ-001` 等稳定ID，分类为 `add`、`modify`、`replace` 或 `remove`。涉及公共API、数据、权限或迁移时自动记录决策 Checkpoint 后非阻塞继续；对账通过前不得重新套脚手架或覆盖现有实现。

成熟已有代码仓库首次接管时进入 `@项目智能初始化`，生成：

生成：

```text
.ai/context/project.json
.ai/context/tech-stack.json
.ai/context/standards.json
.ai/runtime/task.json
.ai/runtime/active-context.md
.ai/governance/locked-decisions.json
.ai/governance/ownership.json
.ai/quality/policy.json
```

大型或多Agent项目由路由按需加载 `@项目状态与上下文管理`，生成 `PROJECT_STATE.md`、`CURRENT_CONTEXT.md`、`CHANGELOG.md`、`ARCHITECTURE.md` 和 `.ai/governance/project-state.json`。

## 二、开始一个长期任务

```text
@可中断任务控制
开始任务 REQ-RESOURCE-001：实现教材资源管理。连续执行；用户中途插入调整时保留已完成工作并修订计划。
```

自然语言控制：

- `暂停当前任务`
- `查看当前状态`
- `调整方向：Viewer 改为统一 Renderer 模式`
- `继续执行`
- `创建检查点：组件完成`
- `请求回滚到 checkpoint-003`（默认只生成回滚计划，不自动破坏代码）

长期、多会话或频繁压缩任务同时使用 `@有界上下文记忆`。01号把活动工作集限制在固定大小，04号把Task ID、Agent交接、Worktree和合并状态持久化。可随时检查：

```text
@有界上下文记忆
显示当前工作集字符数、保留/已收敛checkpoint数量、事实源和恢复下一步。
```

系统不承诺逐字永久保存完整聊天；它保证关键需求、决定、任务状态、风险、证据、Git事实和当前 Skill 路由态在压缩前写入项目事实源。旧 Checkpoint 会压缩进入 `.ai/archive/checkpoints/` 冷归档，并在热区账本保留路径和哈希；需要时按名称或时间点读取，日常不会扫描整个归档。

即使一直使用同一个超长会话，每次压缩前也必须生成 `PreCompact` Checkpoint；压缩后先重新显示轻量路由回执，再校验任务、Git、锁定决定、路由指纹和五插件套件指纹。指纹一致才恢复原来的最多两个活跃原子 Skill，阶段或插件版本改变则重新路由。

`.ai/tasks/` 数量很大时，日常状态、创建任务和 Checkpoint 只读取 `task-index.json` 中的活动 Task ID；完整 Task JSON 仍保留作事实源。全量历史一致性扫描只在用户明确要求审计时运行，避免工程年限越长越慢。

## 三、建立Task ID与任务分流

```text
@工程任务生命周期
创建 KG-001，记录目标、影响文件、负责人、feature分支和验收条件。
```

```text
@任务分流与会话规划
把需求按B/S浏览器前端+服务端、C/S客户端+服务端、契约数据、审核、测试、文档、合并和发布控制拆分。只读探索用 Subagent；并行写入用独立 Worktree。
```

桌面任务创建前，查询错误和超时都不是“没有任务”；必须得到明确空结果并通过项目环境预检。开发完成后冻结只读候选，Review/Test/Merge 全程使用同一个候选 ID；代码有任何变化就创建新候选。反复修复时每轮只允许一个根因假设，同一问题连续两次被证据否定就停止修改并转入根因诊断。

大规模回归执行前先做测试工具预检。跨会话、跨 Agent 或交给外部评审的材料先做敏感信息扫描与脱敏复扫，禁止把密码、令牌或私钥原文放入交接包。

插件不能在普通 Chat 中凭空创建持久会话；在 Codex 中可使用 Subagent 线程和桌面端 Worktree 会话。主线程只保留需求、决策和汇总，原始日志留在子线程或 `.ai/logs/`。

## 四、并行开发

```text
@Worktree任务管理
为 KG-001 的不同写入任务创建独立 Worktree；feature/bugfix基于develop，hotfix基于main，分配所有权并输出路径。
```

不要让两个写入 Agent 在同一个物理工作树同时编辑。

项目默认最多同时存在两个活动写任务、两个处于审核或测试的待收敛任务。长期项目恢复或任务列表变多时运行任务对账，先发现丢失分支、孤儿 Worktree、陈旧文件锁和合并债务，再决定是否继续开新任务。

修改Unity Scene/Prefab/ProjectSettings/meta、NodeTS核心Service、migration或API Contract前使用 `@多Agent文件锁`；合并前释放。

## 五、设计就绪与质量审核

编码前先执行独立复审：

```text
@设计就绪独立复审
从当前需求、工作流、路由、验收卡和测试映射动态构建追踪链，独立检查设计是否足以实现和验收。输出 P0/P1/P2、置信度、未知项和允许进入的下一阶段；存在 P0/P1 时不得进入编码。
```

设计自检不能替代这次独立复审。整改后只回归受影响链路，并再次独立复审，直到 P0/P1 清零或明确阻塞。

代码或设计发生变化后执行风险审核：

```text
@完整变更风险评估
评估暂存、未暂存和未跟踪文件，结合工程图谱生成风险报告；对需求或设计变化执行增量影响分析，并判断是否需要重新执行设计就绪独立复审。
```

随后：

```text
@回归测试范围规划
根据风险报告和真实 package scripts / Unity 配置生成测试计划，不要把未执行测试写成已通过。
```

## 六、发布

```text
@发布就绪审核
检查构建、测试、迁移、回滚、版本和已知风险证据，输出 PASS / WARNING / FAIL。
```

发布前先用 `@功能验收闭环` 确认实现Commit、Review/Test PASS、截图或日志、CHANGELOG、ARCHITECTURE和项目状态均已闭合，再由Merge Agent执行合并预检。

## 七、架构思路如何被主动挑战和补全

当用户提供系统架构、功能架构、模块拆分、技术方案或改造思路时，轻量路由按需加载“架构决策挑战与补全”。用户的业务目标和明确约束会保留，但列出的组件与做法只是待验证假设，不会直接变成最终设计。

```text
@架构决策挑战与补全
这是我的功能架构思路。保留业务目标，主动找出我没想到的缺口、反例、耦合和演进风险；给出有真实权衡的替代方案，不要直接编码。
```

检查范围包括模块边界、异常状态、数据一致性、接口与第三方契约、安全权限、网络与可靠性、性能成本、部署演进、测试和运维，但不会机械展开全部维度。系统先按影响、发生可能性、不可逆程度和决策成本排序，只深入会改变当前决定的少数风险。

输出用 `GAP-*`、`CONFLICT-*`、`ASSUMPTION-*`、`RISK-*` 和 `DEC-*` 保持可追踪；替代方案最多三个，且必须有不同的真实权衡。重大平台、核心技术栈、数据模型、部署、安全边界或公共契约变化自动生成决策 Checkpoint，记录完成后非阻塞继续，不弹出审批；只有缺少必需外部事实或权限、或将执行不可逆高影响操作时才由对应安全门禁暂停。

从零项目先建立 `REQ-*` 需求账本，再挑战方案；存量项目先建立带代码或测试证据的 `CAP-*` 能力基线，再挑战改造边界。这样既避免机械照抄用户思路，也避免脱离现有工程重画一套理论架构。

## 八、UI交互冲突的自动升级

设计、实现或修改 Web、桌面、移动、嵌入式和 Unity 界面时，轻量路由先选择当前阶段的主 Skill，不默认叠加全部 UI 与质量能力：

```text
界面设计 → 当前平台界面设计
组件实现或修改 → 当前平台组件实现
现有界面审核 → 当前平台质量审核
```

主 Skill 在当前任务范围内发现以下风险时，再按需交给“交互状态与冲突治理”：

- 下拉框、菜单、弹窗、抽屉、Popover、Tooltip、选择器、编辑器等隐藏表面；
- 异步搜索、请求乱序、页面卸载后旧结果写回；
- 连续点击、重复提交或危险写操作自动重试；
- 多层浮层、焦点恢复、键盘/手柄/触摸或快捷键冲突；
- 未保存导航、权限中途变化、跨窗口或跨模块状态。

静态页面、普通按钮、无网络的简单局部展开不会额外加载。交互治理只检查当前模块显式契约；无契约时立即返回不适用，不扫描全仓。即使项目很大，每轮仍最多加载两个原子 Skill。

明确要求“检查交互冲突、请求乱序、重复提交、浮层或快捷键冲突”时，路由可以直接选择“交互状态与冲突治理”。

## 九、复杂长链路如何防止越改越乱

当任务跨模块、跨仓库、需要真实外部执行或部署，发生回滚、用户纠正、重复失败，或者同一功能已经出现多份新旧实现时，轻量路由会按需加载“长链路变更收敛”。它不会扫描全仓，也不会保存具体业务规则，只维护当前 Task 的有界控制状态。

必须为用户目标建立稳定验收 ID，并分别声明需要静态、集成、运行时、用户可见还是生产证据。编译、合同测试和接口成功不能替代真实用户效果；需求、策略或代码指纹变化后，旧 PASS 不再自动沿用。

同一业务职责只能有一个活动实现路径。临时迁移兼容必须写明退出条件，合并前完成切换、回归和旧路径退役，并提供删除提交或调用图不可达证据。这样可以阻止同一个功能持续出现 v2/v3、旧入口、重试入口和不同数据装配路径。

真实、计费、生产或不可逆实验必须先登记假设、预期观察和停止条件，任何时刻只允许一个未结实验。同一验收条件连续两次失败后必须重新定方案，不允许继续添加第三层补丁。

范围扩大、用户纠正、证据矛盾、方案失效、回滚、实现路径分叉或部署版本漂移时，对话中会显示一次中文“工程状态告警”，说明出现了什么、影响哪些旧结论、正在如何处置和下一道门禁。告警指纹不变时不会重复，避免长期会话越来越重。

复杂总控还必须分别报告“业务价值进度”和“治理进度”。修复控制账本、validator、测试夹具或会话绑定不等于业务功能已经开始实现；连续两个治理周期没有业务增量时，第三轮必须先复用证据、缩小验证范围或明确换轨理由。相同 Gate、源码/合同指纹和验证范围已有 PASS 时不再全量重跑；夹具或汇总器错误记为 `INVALID`，只补受影响切片，不把工具失败算成产品失败。

只有总控负责桌面任务与 Worktree 生命周期。它按“项目 + 仓库 + 角色族”维护固定槽：实现/修复复用 writer，审核/测试/复验复用 assurance；Task、Candidate 或 base SHA 变化不能成为新建会话的理由。普通任务结束后自动生成 Checkpoint、释放锁与任务资源并进入 `IDLE_REUSABLE`；项目终态自动归档任务并验证本地工具运行时释放，不需要用户确认。

任务只返回 `clientThreadId` 时保持 `SETUP_PENDING`。必须先查询真实任务、等待 pending lease 到期并确认没有 `threadId`，才允许创建；延迟任务一旦出现，立即冻结重复同族槽并保留唯一会话。归档成功但运行时无法证明已经释放时进入 `ARCHIVED_RUNTIME_UNVERIFIED`，总控自动复查且不得继续创建替代会话。自动回收不授权强杀进程、强删 Worktree、删除分支或丢弃未提交修改。

## 十、全局自动应用与可见回执

个人安装器默认把 `templates/GLOBAL_AGENTS_AI_ENGINEERING.md` 性能内核安全合并到 `~/.codex/AGENTS.md`，并默认只保留一个活动插件缓存版本。安装完成后，`plugin_activation.status=activated` 与 `verification.ok=true` 只证明文件、缓存和配置一致；已经创建的旧任务不能可靠原地替换其上下文，必须先Checkpoint并停止写入，再由新任务核对五插件完整版本和套件指纹后接管。若新任务仍指向旧缓存，重启桌面端后再次新建任务。版本漂移期间普通开发路由会被阻断，禁止新旧规则共同修改项目。

日常修改只运行受影响插件测试：

```powershell
py -3 -X utf8 .\tools\run_all_tests.py --plugin ai-engineering-core
```

五插件完整单元测试、一致性审核、路由性能和发布包验证只在套件发布收尾执行，避免普通项目长期停留在治理与全量验证阶段。

## 十一、动态并行、治理退出与长期总控

默认 `parallel_mode=auto-safe`，用户不需要每次写“并行”。ChatGPT先根据变更契约、依赖图、仓库和真实写范围提出所有权通道；常见B/S/C/S通道可以直接复用，大型纯后端、多仓库或同一技术表面存在独立模块时使用 `implementation_lanes` 动态描述。规划态最多8个通道，任何时刻最多2个活动writer。

每个动态通道必须声明稳定ID、技术表面、仓库键和写范围。父子目录、同一公共契约、数据库迁移、权威状态写入者、Unity受保护资产或共享测试环境重叠时强制串行。派发守门器返回 `BLOCK_SCOPE_CONFLICT` 时只等待冲突通道释放，不能通过改Task ID或通道别名绕开。

治理不是长期阶段。满足变更契约、行为不变量和最低回归后，如果连续两个周期只增加控制文档、矩阵或门禁而没有业务源码、可运行能力或真实验证增量，状态机会自动进入首个可执行Development切片并记录 `GOVERNANCE_BUDGET_EXIT_TO_DEVELOPMENT`。只有缺少必需外部事实、权限或不可逆操作门禁时才真正等待。

项目总目标保存在 `.ai/governance/goal-contract.json`，包含稳定ID、修订号、验收ID、不做事项、不变量、约束和指纹。Task创建时绑定当前修订；目标变化后旧Task会被阻断，必须执行目标重绑定，不能在聊天压缩后继续按旧目标开发。

根 `CURRENT_CONTEXT.md` 只保存总控有界摘要；每个活动Task使用 `.ai/runtime/task-contexts/<Task-ID>.md`。Task历史超过策略上限后转入 `.ai/archive/task-history/` 并保留哈希链；`status`、`quick`和会话恢复只读取活动索引，不扫描全部历史。

总控用会话纪元避免永久变慢。达到有效轮次、工具调用、输出字符或压缩阈值后，先生成Checkpoint，再创建唯一替代总控、验证接管并归档旧总控运行时；Task切换本身不会创建新总控。插件不能从桌面端物理删除既有聊天文本，因此真正降低超长任务负担必须采用这种“单一替换而非无限新增”的轮换。

运行长命令时使用 `bounded_run.py`：完整 stdout/stderr 先脱敏并写入 `.ai/evidence/tool-output/`，对话只接收首尾摘要、退出码、证据路径和SHA-256。桌面任务查询失败或超时只禁止盲建替代会话；不需要新隔离运行时的工作以 `CURRENT_THREAD_BOUNDED` 继续，确实依赖新运行时的步骤才进入队列。
