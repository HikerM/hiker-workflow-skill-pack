# 架构决策挑战与补全

## 核心立场

保留用户真正要实现的目标，但不默认用户提出的结构、组件或技术路线已经正确、完整。把用户输入拆成：锁定需求、偏好、方案假设、未知项和禁止事项。既不得机械照抄，也不得为了展示能力而无依据推翻用户。

用户方案始终是待验证假设；分析深度受当前决策影响和证据约束，禁止无边界过度设计。

当当前架构产物存在已证实的消费者、维护者、运维者、数据所有者或失败恢复影响时，由模型动态选择本次适用视角并引用事实；不得把这些示例固化为每次架构决策的角色清单，也不得由 Runtime 根据架构标签生成视角。

## 开始前

1. 确认当前项目身份、阶段和决策范围。
2. 从零项目读取需求账本、验收条件和约束；没有时先进入「0→1需求融合与选型」。
3. 存量项目读取能力基线、真实技术版本、公共契约和关键测试；没有证据时先进入「项目智能初始化」与「存量源码需求对账」。
4. 将用户方案保存为候选，不把它直接写成已批准架构。

## 挑战流程

### 1. 还原目标而不是复述方案

先回答：要解决的用户任务、业务结果、原有行为不变量、容量与时延目标、可接受失败、部署环境和演进期限分别是什么。无法确认的内容标记 `unknown`，不得自行补成事实。

### 2. 构造反例

只对当前决策相关的高风险维度提出反例：

- 职责与边界：模块是否拥有多个变化原因，公共能力是否被重复实现，依赖方向是否反转；
- 工作流与状态：正常路径之外，取消、超时、重试、重复提交、部分成功、恢复和回滚如何处理；
- 数据与一致性：事实源、生命周期、事务边界、并发写、幂等、顺序、缓存失效和迁移兼容；
- 契约与集成：前端/客户端、服务端、数据库、消息、第三方和设备间的版本、错误与降级契约；
- 安全与权限：身份、授权、租户隔离、敏感数据、审计和最小权限；
- 可靠性与网络：断网、抖动、限流、第三方不可用、容器间传输失败和重放；
- 性能与成本：关键路径、热点、背压、容量上限、资源占用和可观测成本；
- 发布与演进：灰度、兼容窗口、迁移顺序、回滚、旧路径退役和未来扩展；
- 验证与运维：可测试边界、运行证据、日志指标追踪、告警、故障定位和所有权。

不要机械展开全部维度。先按影响、发生可能性、不可逆程度和决策成本排序，只深入前几项真正会改变架构的风险。

### 3. 建立缺口与假设账本

为每项使用稳定ID：

- `GAP-*`：用户方案遗漏；
- `CONFLICT-*`：要求或边界冲突；
- `ASSUMPTION-*`：尚未验证的关键假设；
- `RISK-*`：有影响路径的风险；
- `DEC-*`：需要锁定的架构决定。

每项必须包含证据、影响、是否阻断、验证办法和最迟决策时间。不得用“最佳实践”四个字代替项目证据。

### 4. 生成替代方案

只有确有决策差异时才给出候选，最多三个。每个候选说明：

- 保留了用户思路中的什么；
- 改变或拒绝了什么及原因；
- 模块、数据、契约和部署边界；
- 对可靠性、性能、安全、复杂度、交付速度和后续演进的影响；
- 迁移、回滚、测试和运维成本；
- 仍然未知的条件。

候选不能只是技术名不同而架构权衡相同，也不能默认最复杂方案最强。

### 5. 给出独立建议

明确输出“保留、修改、否决、待验证”四类结论，并说明置信度和证据。发现用户没有想到的重要问题时主动提出；发现用户方案已经合理时同样应说明为什么，不强行制造反对意见。

平台、核心技术栈、数据模型、部署方式、安全边界或公共契约发生重大变化时，必须自动生成决策 Checkpoint，记录候选、证据、风险、回退和推荐选择后非阻塞继续，不得弹出审批。决策记录完成前不得批量生成正式代码；缺少必需外部事实或权限、或即将执行不可逆高影响操作时，才进入对应安全门禁。

## 输出契约

输出保持有界并可决策：

1. 用户目标与必须保留的意图；
2. 已验证事实、关键未知项和被推翻假设；
3. 按优先级排列的架构/功能缺口；
4. 最多三个真正不同的方案及权衡；
5. 推荐方案、反对理由和适用前提；
6. 自动记录的 `DEC-*`、推荐选择及允许用户后续覆盖的条件；
7. 架构不变量、验收条件和下一步验证。

## 与其他能力的边界

- 「0→1需求融合与选型」拥有从零需求账本与技术决策流程；本能力负责挑战其中的架构假设。
- 「存量源码需求对账」拥有现有能力基线；本能力不得绕过基线重画理想架构。
- 「设计就绪独立复审」审核方案是否可实现、可验收；本能力不自行给复审 PASS。
- 「完整变更风险评估」审核已经发生的完整变更；本能力面向编码前决策，不冒充变更审核。

## 禁止

- 不因为用户给了详细思路就停止独立分析；
- 不把没有证据的猜测包装成用户遗漏；
- 不一次性引入微服务、消息队列、缓存、事件溯源等全部复杂设施；
- 不脱离真实规模、团队、预算、部署和运维能力追求理论完美；
- 不直接修改源码、合并、推送、部署或发布。
