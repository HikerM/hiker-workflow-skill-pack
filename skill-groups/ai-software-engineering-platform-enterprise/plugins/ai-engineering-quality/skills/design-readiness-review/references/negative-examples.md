# 通用负例

| 负例 | 独立复审结论 |
| --- | --- |
| 页面有名称但没有数据或 API/命令契约 | 引用完整度不足；若影响核心路径实现或验收，至少为 P1 |
| API 只有“保存内容”但没有请求响应 Schema | 命令语义不可实现、不可做契约测试；按影响评为 P1，若可能覆盖/丢失关键数据可为 P0 |
| 数据只有 `payload_json` 但没有类型 Schema | 结构、约束、引用和版本被隐藏；复杂表面不得通过 |
| 需求有测试 ID 但核心页面没有测试 | ID 和数量不能替代可执行核心流程场景；至少为 P1 |
| UI 只显示成功态 | 失败、加载、空、权限和恢复由实现者猜测；按实际工作流影响分级 |
| 复杂页面没有并发、失败、降级和发布边界 | 存在覆盖、丢失、不可用或错误公开风险；通常为 P1，严重数据/发布风险为 P0 |
| 内部 ID、对象键、错误堆栈或权限代码暴露给用户 | 信息隔离失败；按敏感度、可利用性和影响评为 P0 或 P1 |
| 自检 `PASS` 但独立设计深度不足 | 保持独立发现的等级；自检结论不得覆盖 P0/P1 |
| 组件仅命名为 `Editor`、`Canvas`、`ContentArea`，没有真实责任和契约 | 组件存在性为假完整，必须回到领域对象、输入输出、命令和状态 |
| 当前需求、页面与测试一起删除同一项并仍互相一致 | 与批准基线比较后视为疑似未批准范围删除；无法确认时阻断 |
| 编辑、阅读、审核、发布各有界面，但未定义数据版本与投影关系 | 预览和公开结果不可判定，涉及发布时至少为 P1 |
| 整改只给页面文档补一句说明，数据、API 和测试仍沿用旧契约 | 发现未闭合，相关 P0/P1 保持打开 |
