# 追踪与语义充分性清单

## 目录

- 独立范围与基线
- 动态追踪链
- 节点充分性
- 跨切面审核
- 自检门禁盲区
- 增量复审闭包

## 独立范围与基线

1. 按项目配置和产物登记解析批准需求基线、批准范围变更和当前需求，不预设文件名、目录或数量。
2. 从角色、目标、业务规则、工作流和验收结果独立提取需求集合；保留原始标识和来源锚点。
3. 当前需求、页面、测试或证据集合即使相互一致，也要与批准基线或签署清单比较。同步缺失可能是协同误删，不是自动缩减范围。
4. 记录审核输入的版本或内容指纹。来源变化、冲突未决或基线缺失会降低置信度，并可能阻断结论。

## 动态追踪链

对项目中实际适用的关系建立链：

`需求 → 工作流 → 页面/交互表面 → 设计系统/Token → 组件 → 数据 → API/命令/事件 → 权限 → 测试 → 证据`

关系可以一对多或多对一。后台过程可能没有页面，静态表面可能没有写命令；此时保留链并标记不适用理由。不要为满足模板伪造节点，也不要用空白表示已审核。

每一关系记录：上游和下游来源锚点、适用版本、关系语义、完整性、充分性、未知项和发现编号。集合大小只作为导航信息，不作为通过条件。

## 节点充分性

| 节点 | 足以实现和验收所需的内容 |
| --- | --- |
| 需求 | 角色、目标、业务规则、约束、成功结果、边界和可判定验收 |
| 工作流 | 触发、前置、主路径、替代/失败路径、状态转换、结束与恢复 |
| 页面/表面 | 入口出口、任务与信息层级、构图语法、真实数据/动作、全状态、响应式和无障碍；不能只给通用后台骨架 |
| 设计系统/Token | 项目视觉方向、语义色彩与对比、间距尺度与使用规则、排版、形状层级、交互状态和主题映射 |
| 组件 | 业务语义、输入输出、事件、状态归属、权限、复用/扩展/组合/新增判定、变体与隔离边界 |
| 数据 | 类型字段、约束、不变量、标识、引用、版本、生命周期、兼容与敏感级别 |
| API/命令/事件 | 请求/响应 Schema、鉴权、校验、幂等/顺序、错误、状态效果、版本与可观察证据 |
| 权限 | 角色/主体、对象、动作、字段、状态、允许/拒绝规则、前后端执行和拒绝体验 |
| 测试 | 前置数据、用户/系统动作、可观察断言、失败/边界覆盖、契约锚点与运行条件 |
| 证据 | 编码前定义与测试/契约关联的证据类型、采集点、观察内容和保存责任；已有结果时再核对同一版本/范围、状态与新鲜度 |

只给名称、截图、自然语言“支持保存”、测试 ID、接口路径或“沿用现有”不满足语义充分性。外部契约可以复用，但必须可解析、版本匹配且内容达到同样深度。

## 跨切面审核

### 反模板与视觉系统

- 将页面构图回溯到核心任务、阅读路径和内容关系；默认侧栏、顶栏、指标卡与等宽卡片网格不是充分设计证据。
- 区分“项目技术上使用 Bootstrap”和“视觉上照搬 Bootstrap 默认语法”。允许兼容既有依赖，但必须有独立 Token、主题适配和组件契约。
- 逐处检查卡片是否承担独立理解、整体操作、权限边界或响应式重排语义；仅为留白、分组或阴影而套卡片视为不足。
- 检查核心页面是否有主焦点、疏密节奏、层次变化和服务任务的签名元素；所有内容等权、等色、等容器的“干净”页面仍属于视觉不足。
- 检查渐变、图形、阴影、动效和品牌元素是否服务识别、比较、定位、因果反馈或空间连续性，而不是用装饰掩盖层级问题。
- 抽查跨页面的色彩、间距和组件映射，避免只在主页面补齐 Token 文档而其他页面继续硬编码或复制组件。
- 关键页面必须有目标分辨率和关键状态证据；仅凭一张美化后的成功态截图不能证明系统性。

### 用户可见信息隔离

- 识别所有用户可见字段、URL、复制/导出、通知、错误和辅助技术文本。
- 检查内部标识、对象键、原始异常、跟踪信息、权限代码和敏感元数据是否被投影为安全、可理解内容。
- 检查拒绝和不存在对象的响应是否避免泄露资源与权限规则；前端隐藏不视为授权证据。

### 编辑、阅读、审核与发布一致性

- 对实际存在的模式比较内容结构、字段含义、媒体、引用、排序、权限、可见性、空值、失败、无障碍和响应式。
- 核实每种模式读取草稿、审核版本、候选快照还是已发布快照；转换、预览、发布和回滚必须可测试。
- 检查审核批注、内部状态和未发布变化不会进入公开投影，历史发布不会被当前编辑隐式覆盖。

### 共享契约

- 数据、事件、权限、组件和发布模型有变化时，反向核对所有消费者及测试。
- 页面文档新增说明但共享契约和验收未同步时，不能判定整改闭合。

## 自检门禁盲区

独立复审必须主动寻找：

- 只比较需求数、页面数、测试数或 ID 是否相等；
- 只验证引用目标存在，不读取目标内容与版本；
- 只匹配关键词或必填标题，不检查 Schema、状态转换和失败语义；
- 测试映射存在，但场景没有前置、步骤、断言或核心流程覆盖；
- 多个文档共同误删同一项后仍被判为一致；
- 自检使用当前设计自身作为需求基线；
- 旧自检或旧复审没有绑定当前内容指纹；
- 以设计者声明、截图或自动计数总分抵消阻断缺口。

先完成独立判断，再对照自检；若结论差异，记录自检未捕获的规则和证据，不接受简单改写 `PASS`。

## 增量复审闭包

从需求差异或整改点计算：

1. 直接受影响的需求、工作流和表面；
2. 下游组件、数据、API/事件、权限、测试和证据；
3. 共享契约的其他消费者与反向依赖；
4. 用户可见信息、跨模式、并发、发布等横切面；
5. 先前发现及其回归断言。

仅当未受影响节点的来源、共享依赖和指纹均未变化时，才能继承旧结论。整改验证要检查契约内容和相关回归，不以文件已修改或字数增加为完成证据。
