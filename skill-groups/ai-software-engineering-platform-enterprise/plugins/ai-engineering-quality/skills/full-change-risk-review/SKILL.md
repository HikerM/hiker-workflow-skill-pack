# 完整变更风险评估

## 职责边界

- 收集并审核完整真实变更集，输出事实、风险、置信度、未知项、控制建议和所需证据。
- 判断设计就绪结论是否因语义变更而失效，并计算需要重开的追踪链；不重新执行 UI 设计、不替设计者补契约、不把风险审核冒充设计复审。
- 保持只读，不修改源码或设计，不自动合并，不把计划中的测试或复审写成已通过。
- 审核对象必须绑定不可变 `candidate_id`；审核期间发现源码、索引、提交或工作区指纹变化时立即标记 `STALE`，禁止继续给旧候选出 PASS。
- 阅读 [设计变更影响清单](references/design-change-impact.md) 处理设计相关变更。

## 输入发现

1. 优先使用包含暂存、未暂存和未跟踪文件的完整本地变更模式；也可审核明确提交范围、文件清单或用户提供的需求差异。
2. 从项目配置和产物登记解析风险策略、代码所有权、批准需求基线、设计/测试证据、可选工程图谱及其版本；不要预设项目目录或文件名。
3. 若用户在对话中新增或改变要求，将其作为显式需求差异输入，并区分“尚未落盘”与“已进入批准基线”。

## 审核流程

1. 验证变更集完整性，识别新增、修改、删除、重命名、二进制和无法读取的内容；排除生成物时保留规则与证据。
2. 结合产物登记、内容语义和差异上下文分类变更。不要只按路径或扩展名推断需求、架构、数据、API/事件、UI、权限、测试和发布影响。
3. 对任何语义设计变更或显式需求差异，比较批准基线与当前版本，从变化节点沿追踪关系向下游、共享依赖和反向消费者扩散，得到受影响设计层与必要回归范围。
4. 判断 `design-readiness-review` 是否必须重跑。若需重跑，记录原因、受影响范围、所需输入和旧结论失效依据；不得直接宣称复审已通过。
5. 审核整改闭包：先前设计发现是否真正同步到数据、API/事件、权限、状态、验收与测试，还是只修改页面说明、标题、计数或链接。
6. 将设计影响与代码、数据迁移、认证授权、密钥、发布配置、所有权、图谱和测试风险合并，输出分级发现、置信度、未知项和控制建议。
7. 对受治理任务运行 `python <plugin-root>/scripts/risk_review.py --root . --task-id <TASK-ID>`；该命令同时执行架构守卫，核对变更契约、影响半径、依赖方向、公共表面、消费者、原有行为不变量、最低回归和文件增长预算。高严重度发现必须把总体风险至少提升为 HIGH。
8. 风险审核同时运行交付洁净度门禁：正式运行路径不得默认启用 Demo/Mock/Fixture，不得把占位文案、样例用户、内部路径、堆栈或数据库错误直接暴露给用户。命中项只报告代码、路径和行号，不回显可能的敏感内容。

## 插件套件增强收尾

当被审核对象是本智能工程插件套件，且任一插件、Skill、路由、注册表、安装器或发布包发生变化时，普通变更集审核不能替代套件一致性审核。结束前必须运行：

```bash
python <suite-root>/tools/audit_skill_coherence.py --root <suite-root>
```

该门禁一次性审核五个插件的全部 Skill，检查注册归属、职责类型、修改权限、唯一隐式入口、路由覆盖、正向Eval、中文名称、默认调用提示、本地引用、触发描述重叠、未授权高影响操作和 Skill 体积。只有 `ok=true` 才允许打包或宣告增强完成。它只用于插件套件开发与发布，不进入普通项目任务，不在日常路由阶段扫描全部 Skill。

## 大型工程渐进治理

- 默认按目录、依赖和真实变更自动识别模块；模块登记、依赖规则、运行拓扑为空时，不因“未配置完整”阻断普通局部改动。
- 只有跨模块公共接口、共享资产、迁移、受保护模块或源码无法推断的运行关系需要显式登记；禁止复制全仓事实到配置中。
- 任务变更契约只描述本次允许范围、必须保持的行为和最低测试，不保存实现细节；变更范围扩大时由 Planning Agent 显式更新并留下历史。
- 文件预算是风险信号，不按行数机械拆分；超过阻断阈值时必须先明确职责边界、依赖方向和迁移步骤，避免把一个大文件拆成多个互相穿透的小文件。
- 架构守卫证据绑定 Git HEAD 与工作区指纹；代码变化后旧证据自动失效，Review、Testing、Merge 不得复用过期结果。

## 设计复审触发规则

出现以下任一语义变化时，标记需要对受影响范围重新执行独立设计就绪复审：

- 角色、目标、业务规则、工作流、页面/交互表面、状态或验收结果新增、修改、删除；
- 架构边界、共享组件责任、领域数据、Schema、引用、版本或生命周期变化；
- API、命令、事件、错误、幂等、顺序、权限、并发、恢复、降级或发布语义变化；
- 验收卡、测试映射或证据要求变化，使原追踪链、覆盖结论或可执行断言失效；
- 对先前 P0/P1 的整改，或当前设计/需求指纹与独立复审所绑定的指纹不一致；
- 多个当前文档共同删除批准基线中的项目，或基线本身缺失、冲突、未经批准地变化。

仅格式、拼写或不改变语义与来源锚点的整理可不重跑，但必须给出差异证据。复审范围由影响闭包决定，不因小改动默认全量，也不因文件少默认局部。

## 输出契约

按项目配置的证据登记方式输出：

- 变更模式、范围、基线/目标版本、完整性、忽略项和不可读项；
- 风险等级、事实证据、置信度、未知项、所有权与可选图谱状态；
- 显式用户需求差异、受影响设计层、追踪闭包和必要回归范围；
- 是否必须重新独立设计复审、触发原因、旧结论有效性及允许的下一步；
- 表面整改或契约不同步发现，以及需要补齐的证据。

所有集合和统计从当前变更、批准基线及项目登记动态计算。若需要设计复审但没有同一指纹、同一范围且无 P0/P1 的独立结论，不得输出“低风险且可直接进入编码/发布”。

## 阻断事项

出现以下情况不得给出低风险直行结论：

- 变更集收集失败、不完整或关键内容不可读；
- 数据迁移、认证授权、密钥、发布配置等关键路径变化而缺少控制证据；
- 结论依赖的图谱、需求基线、测试证据或设计复审已过期；
- 关键范围没有所有权、测试映射或可验证的回滚/兼容依据；
- 删除或重命名公共契约而没有消费者分析与兼容证据；
- 设计语义已变化但未完成所需的独立设计就绪复审；
- 整改仅改变表面文档，相关数据、API/事件、权限和测试契约仍不一致。
- 实际改动超出任务契约、公共表面变化没有消费者回归、影响图谱过期/截断、依赖方向违规或文件增长超过阻断预算。
- 正式运行路径默认启用演示或Mock数据，或用户界面泄漏占位、内部诊断和本机信息。
