# B/S UI 与交互设计

## 准备设计上下文

1. 从项目初始化状态和项目配置解析仓库根、技术栈、组件库、状态管理、设计产物登记方式与证据位置；缺少初始化状态时调用 `project-bootstrap`，不要自行假定框架或目录。
2. 从当前有效的需求规范、批准基线、工作流、导航/路由规范、验收卡、测试映射、既有设计和实现中动态建立来源清单，记录版本、来源锚点和冲突。不得用预设数量或单一文档目录代替发现。
3. 以批准需求基线或批准清单为独立参照，核对当前集合。多个当前文档相互一致不代表删除有效；无法确认的缺失必须列为未知项。
4. 阅读 [复杂度与设计深度](references/complexity-rules.md)、[设计系统与反模板约束](references/design-system-and-anti-template.md) 和 [动态追踪与一致性清单](references/traceability-checklist.md)。只有当前表面包含编辑器、复杂表格、树、拖拽、图表、虚拟列表、上传或同等级能力且项目内没有成熟实现时，才读取 [开源UI能力选型](references/open-source-ui-capability-selection.md)；普通控件不得为“找轮子”联网扩张。自检时再阅读 [通用负例](references/negative-examples.md)。

## 核心工作流

1. 从角色目标、工作流入口与结果、导航/路由和验收场景发现页面及交互表面；区分独立页面、嵌入式工作区、对话框/抽屉、后台过程和跨页面状态，不为凑清单虚构页面。
2. 为每个表面记录需求与工作流来源、用户角色、入口/出口、所属核心流程、实际技术约束和复杂度理由。
3. 按复杂度规则选择标准设计或深度设计。出现结构化编辑、富文本、媒体资源、空间画布、实时通信、自动保存、并发、发布快照、多角色权限、大文件或离线恢复等信号时，不得按普通信息页处理。
   对下拉框、菜单、弹窗、抽屉、Popover、日期/树选择、编辑器、上传和响应式导航等隐藏表面，建立稳定交互 ID、状态转换、并发/取消、浮层/焦点和非默认状态证据；出现跨模块或运行时冲突风险时，交给 `interaction-conflict-governance` 做有界检查，不在本 Skill 复制全量规则。
4. 在画页面前建立项目专属视觉方向与最小设计系统：明确视觉性格、信息密度、层级语法、语义色彩、间距尺度、字体、形状和反馈；审计现有 Token 与组件，优先复用并记录新增理由。
   同时为每个核心页面记录一个紧凑构图契约：`primary_task`、`composition_pattern`、`focal_point`、`reading_path`、`density_zones`、`signature_element`、`card_usages`、`non_card_alternatives`。不得新增第二套全量UI账本。
5. 完成页面设计后，建立需求到验收证据的追踪关系，执行用户可见信息隔离与编辑态、阅读态、审核态、发布态一致性检查。
6. 执行反模板与语义自检并记录未解决项；自检只能证明设计者已检查，不能替代 `design-readiness-review` 的独立复审。
7. 根据独立复审的 P0/P1 定向整改受影响契约，回归相关追踪链后再次独立复审。同一基线最多允许一次“设计→独立复审→定向整改→复审”；仍存在同类 P1 时直接报告阻断和缺证，不新增矩阵、会话或治理轮次。

## 反模板硬约束

- 不得默认生成“左侧栏 + 顶栏 + 四个指标卡 + 等宽卡片网格”的普通后台模板；页面结构必须从任务优先级、内容关系和真实工作流推导。
- 不得把 Bootstrap 的默认视觉语法当作设计：包括蓝色主按钮、灰底白卡、统一圆角阴影、`container/row/col` 式机械分栏。项目技术上已使用 Bootstrap 时可以兼容其能力，但必须通过项目 Token 和组件层建立独立视觉语言。
- 不得把每个标题、字段组、图表或操作区都包成相同卡片。卡片只用于语义独立、可作为整体操作或需要明确边界的内容单元；其他内容优先使用排版层级、分区、表格、列表、分隔、工作区或渐进披露。
- 卡片不是默认容器。每处卡片必须通过“移除表面测试”：去掉背景、圆角、边框和阴影后，若内容仍只是普通分组且不损失整体选择、操作、权限或响应式移动语义，则不得使用卡片。
- 不得直接复制组件库 Demo、仪表盘模板或相邻页面骨架后替换文案。若沿用既有模式，必须说明它为何匹配当前任务。
- 不得在没有设计系统、间距规范、色彩规范和组件复用清单时输出“可进入编码”。
- 不得以“简洁”为理由交付没有视觉焦点、层级、节奏和状态表现的单调页面；也不得用无语义渐变、发光、玻璃效果、巨量阴影或无关插画掩盖信息架构不足。

## 标准设计契约

每个适用页面或交互表面至少说明：

- 目标、角色、前置条件、入口、主路径、替代路径和完成结果；
- 信息架构、布局、视觉层级、内容密度、视觉焦点、疏密节奏、导航关系、响应式行为和目标设备约束；
- 适用的 Design Token：语义色彩角色与状态、间距尺度与布局节奏、字体层级、圆角/边框/阴影使用边界，以及明暗模式或品牌变体；
- 使用真实业务语义命名的组件树，以及现有复用组件、新增组件理由、组件职责、输入、输出、变体、状态和交互事件；
- 所读写数据的类型、约束、来源、更新时机与引用关系；静态表面明确标注不适用并说明理由；
- 所调用命令、API 或事件的请求、响应、错误、权限与幂等要求，或指向已审核契约的精确锚点；
- 默认、加载、空、校验失败、业务失败、网络异常、无权限、超长内容和大数据状态；
- 反模板与视觉丰富度检查结果、卡片使用理由、关键过渡/微交互、无障碍、键盘操作、焦点、反馈和敏感信息呈现规则；
- 高复杂度通用能力的 `复用现有/引入开源/自研` 结论；只有触发开源选型时才附最多三个候选及版本兼容、许可证、维护、安全、体积、无障碍、主题适配和退出边界证据；
- 可执行验收：前置数据、用户动作、可观察结果、失败断言和所需证据。

## 高复杂度补充契约

对高复杂度表面，在标准契约之外补齐：

- 可判别的领域数据结构、约束、版本和迁移/兼容边界；
- 语义命令与事件、引用解析、撤销/重做或补偿边界；
- 本地、服务端、同步、权限、审核和发布状态及其转换条件；
- 自动保存、重试、离线队列、恢复点、并发策略、冲突检测与用户决策流程；
- 实时能力或大文件能力不可用时的降级、取消、限额、进度和可恢复失败；
- 草稿、审核版本、发布快照、可见范围、回滚和历史引用的明确语义；
- 覆盖成功、失败、并发、恢复、权限和发布边界的可执行验收。

不得用只表示容器、技术控件或不透明存储形态的占位名替代实际组件、领域模型和命令设计。若某契约由其他已审核产物承载，必须给出可解析锚点和适用版本，不能只写“见后端”或“沿用现有”。

## 增量收敛

- 初次设计覆盖动态发现的完整范围；后续变更只重新打开需求差异命中的追踪链、共享契约和必要回归范围。
- 用户新增或改变要求时，先做影响分析，再同步页面、组件、数据、API/事件、权限、测试与证据；不得只补页面说明。
- 未受影响范围只有在批准基线、来源锚点和共享契约仍有效时才能保持关闭。
- 只有同一设计版本的独立复审不存在 P0/P1，才允许将已复审范围交给编码；P2 必须记录处置方式。

## 输出

按项目配置登记：动态页面/表面清单、复杂度判定、逐表面设计契约、跨模式一致性矩阵、追踪矩阵、自检结果、未知项、设计差异和相关回归范围。所有集合和统计均从本次来源清单计算，不写入通用 Skill 常量。
