# 通用负例

以下负例用于语义自检。命中并不靠关键词计数；应检查缺失内容是否由有效、已审核的外部契约精确承载。

| 负例 | 为什么不充分 | 最低整改证据 |
| --- | --- | --- |
| 页面有名称和布局，但没有数据或 API/命令契约 | 实现者无法判断字段、来源、保存时机、失败和权限 | 类型化数据、交互命令及请求/响应/错误，或可解析的已审核契约锚点 |
| API 只写“保存内容”，没有请求与响应 Schema | 无法确定保存单位、版本条件、幂等、校验和部分失败 | 业务语义命令名、类型 Schema、前置/后置条件、错误与版本策略 |
| 数据只有 `payload_json`，没有类型 Schema | 不透明字段掩盖结构、约束、迁移、引用与兼容问题 | 可判别的类型模型、每个变体字段与约束、未知扩展的边界 |
| 需求带有测试 ID，但核心页面没有测试 | 标识存在不代表关键路径可验收 | 核心工作流到可执行场景的映射、前置数据、步骤、断言和证据 |
| UI 只显示成功态 | 加载、空、校验、网络、权限和业务失败会被实现者临时决定 | 与实际能力匹配的状态集合、触发条件、用户动作和恢复结果 |
| 复杂页面没有并发、失败、降级和发布边界 | 数据丢失、覆盖、不可用或草稿泄露风险未设计 | 并发策略、失败保留、能力降级、快照/可见性和回滚语义 |
| 内部 ID、对象键、错误堆栈或权限代码直接暴露给用户 | 泄露实现、安全信息且不可理解 | 用户可见投影、安全关联码、受控诊断和服务端拒绝策略 |
| 自检为 PASS，但独立复审发现设计深度不足 | 自检可能复用同一假设或只检查数量与引用 | 独立重建的追踪链、语义充分性证据和 P0/P1 清零结论 |
| 组件树只写 `Editor`、`Canvas`、`ContentArea` 等容器名 | 名称没有表达真实业务对象、职责、输入、事件或状态 | 以领域责任命名的组件及其明确契约；视觉容器只能作为实现细节 |
| 多份当前文档同时删除同一需求后仍相互一致 | 一致性检查无法发现协同误删 | 与独立批准基线或签署清单的差异及显式范围变更批准 |
| 编辑态、阅读态、审核态和发布态各自有图但无版本关系 | 不知道各模式读取草稿、审核版本还是发布快照 | 模式到数据版本/投影的矩阵，以及跨模式转换和隔离验收 |
