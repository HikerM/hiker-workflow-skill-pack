# 开源 UI 能力选型

只在项目内没有成熟实现，且当前需求包含编辑器、复杂数据表格、树、拖拽、图表、虚拟列表、上传、日历、命令面板或同等级高复杂度能力时读取本文件。按钮、输入框、普通列表、布局和样式不得触发联网选型。

## 一次性决策

在当前设计步骤内完成，不创建新会话、Agent、治理阶段或长期调研任务：

1. 先核对现有依赖、组件库和项目封装，能够扩展时优先复用。
2. 确实缺失时，根据已识别的框架和版本检索最多三个当前可用候选；只使用官方文档、官方仓库、许可证和发布记录作为关键事实来源。
3. 比较版本兼容、许可证、维护与安全状态、包体/运行性能、无障碍、主题与 Token 适配、SSR/桌面壳等实际运行约束、API 稳定性和替换成本。
4. 选择 `复用现有`、`引入开源` 或 `自研`。没有候选满足硬约束时才自研，并写明具体缺口；不得以“更灵活”为泛化理由重复造轮子。

## 实现边界

- 开源能力通过项目适配层和语义组件封装，页面不得直接依赖第三方内部 API。
- 保留项目自己的 Token、信息层级和交互状态；不得把组件库 Demo 或默认皮肤当成页面设计。
- 只引入当前能力必需的包；禁止为了一个控件导入整套后台模板。
- 记录许可证、锁定版本、升级/替换入口和关键行为测试。
- 安装依赖、改锁文件和启用插件属于实现动作，必须进入本次允许范围并接受构建与回归；设计阶段只做选型。

## 性能与停止条件

- 最多三个候选，满足硬约束后停止扩搜。
- 只输出一张紧凑比较表，不生成市场全景、长篇教程或重复评分矩阵。
- 官方事实不足或候选均不兼容时，在当前设计中记录未知项和自研理由，不停留在调研阶段。
