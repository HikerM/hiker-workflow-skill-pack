# 动态追踪与一致性清单

## 目录

- 来源与集合构建
- 页面与交互表面发现
- 追踪链
- 用户可见信息隔离
- 多模式一致性
- 自检与增量回归

## 来源与集合构建

按项目配置、产物登记表和内容标记发现证据，不假定文件名或目录：

1. 批准的需求基线、决策记录或签署清单；
2. 当前需求规范与变更说明；
3. 角色旅程、业务工作流、信息架构和导航/路由规范；
4. 架构、技术栈、组件注册表、数据与接口/事件契约、权限模型；
5. 页面设计、验收卡、测试映射和已有执行证据。

从证据中提取本次实际的需求、工作流、表面、组件、数据契约、接口/事件、权限规则、测试和证据集合。保留源标识；源中没有稳定标识时，可生成仅在当前审核基线内稳定的语义追踪键，并记录来源锚点。任何统计都由这些集合计算。

若当前文档之间一致但批准基线中的项目同时消失，标记为疑似范围删除。只有显式批准的范围变更才能关闭该项。批准基线缺失时列为未知，不用“相互一致”推断完整。

## 页面与交互表面发现

1. 从每个角色目标、触发条件和完成结果提取用户必须看到或操作的步骤。
2. 将步骤映射到真实交互表面：独立页面、嵌入式区域、对话框/抽屉、跨页面流程或无需界面的后台过程。
3. 与导航/路由规范核对入口、参数、守卫、返回路径和深链行为。需求未规定路由时不要虚构路由。
4. 与既有实现核对复用和迁移约束，但不能用当前实现缺失反向删除需求表面。
5. 合并同义项，保留一对多和多对一关系；页面名称不是完整性证据。

每个表面记录：语义名称、来源锚点、角色、核心工作流、入口/出口、复杂度、适用模式、依赖契约和验收入口。

## 追踪链

建立“需求 → 工作流 → 页面/交互表面 → 组件 → 数据 → API/命令/事件 → 权限 → 测试 → 证据”关系。某一节点确实不适用时记录理由，不能留空或强造对象。

逐链检查两类完整性：

- 结构完整性：引用目标存在、版本匹配、没有悬空或循环替代说明。
- 语义充分性：内容提供实现和验收所需的字段、状态、规则、失败与观察点，而不只是名称或链接。

共享组件、数据或接口变化时，反向查找所有消费表面和测试。核心流程至少有端到端验收入口；高复杂度能力还需覆盖自身识别出的失败和恢复边界。

## 用户可见信息隔离

为每个字段、错误和诊断信息标记受众：用户可见、授权运营可见、仅系统内部或敏感。检查：

- 用户界面使用业务名称、可理解状态和可行动的错误说明；
- 内部数据库标识、对象存储键、消息键、跟踪标识、原始异常堆栈和权限代码不直接展示；
- 复制、导出、URL、通知、审计记录和无障碍文本同样执行隔离；
- 需要客服定位时使用专门的安全关联码或受控详情，而不是泄露底层实现；
- 前端隐藏不替代服务端授权，拒绝响应不暴露对象是否存在或敏感规则。

## 多模式一致性

对项目实际存在的编辑态、阅读态、审核态和发布态建立矩阵；不存在的模式写明来源依据。至少比较：

- 内容结构、字段含义、格式化、媒体、引用和排序；
- 权限、可见性、脱敏、操作入口和拒绝体验；
- 版本来源、草稿/快照语义、更新时间和状态标签；
- 空值、缺失资源、断链、兼容数据和失败回退；
- 响应式、键盘导航、焦点顺序和辅助技术语义。

各模式应共享同一领域语义或给出明确、可测试的投影/转换规则。尤其检查预览是否真的读取待发布快照、阅读是否不会看到未发布草稿、审核批注是否不会进入公开内容、历史发布是否不会被当前编辑覆盖。

## 自检与增量回归

自检不能只计数。逐项回答：

- 页面/表面是否由需求和工作流发现，而非先有页面清单再找引用；
- 数据与命令是否有类型和失败语义；
- 状态是否包含失败、无权限、并发、降级和恢复中实际适用的部分；
- 验收是否能执行并观察到持久化结果或事件，而非只断言“显示成功”；
- 用户可见内容是否通过隔离检查；
- 多模式矩阵是否解释差异和版本来源；
- 所有“见其他文档”是否有有效锚点、版本和充分内容。

用户要求或设计契约变化后，从变更的来源锚点向下游和共享依赖双向扩散，得到受影响链。只回归受影响链及跨切面契约，但若批准基线、共享权限、发布模型或全局数据结构变化，应扩大范围。记录未重开范围保持关闭的证据。
