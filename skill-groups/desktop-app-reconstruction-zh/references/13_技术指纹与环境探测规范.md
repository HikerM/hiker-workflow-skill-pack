# 13 原软件技术指纹与环境探测规范

## 1. 两类技术结论必须分开

### 原软件技术指纹

回答“原软件可能由什么技术构成”。证据可来自源码、项目文件、锁文件、构建配置、合法可读的运行库、安装目录、进程拓扑、窗口行为和资源结构。黑盒情况下只能给候选、证据、置信度和限制。

### 目标实现技术栈

回答“重建软件应采用什么技术”。它由目标平台、性能、系统集成、团队能力、维护周期、许可和 POC 结果决定，不要求与原软件内部技术相同。

任何文件都不得把两者合并成一个未经证明的“技术栈”。

## 2. 探测顺序

1. 确认授权允许检查的目录、程序、日志和运行时观测范围；
2. 完成 `SOURCE_APPLICATION_PROFILE.yaml`；
3. 有源码或合法安装目录时运行 `scripts/detect_project_stack.py`；
4. 人工复核项目文件、锁文件、CI、构建脚本、运行库和工具链证据；
5. 将结论写入 `SOURCE_TECH_FINGERPRINT.yaml`；
6. 每个推断记录证据、置信度、替代解释、限制和下一验证动作。

## 3. 源码模式的高价值证据

| 技术 | 常见证据 | 可确认内容 |
|---|---|---|
| .NET/C# | `global.json`、`*.csproj`、`Directory.Build.props`、锁文件 | SDK、TargetFramework、LangVersion、WPF/WinForms/WinUI、包版本 |
| Unity | `ProjectSettings/ProjectVersion.txt`、`Packages/manifest.json`、`packages-lock.json` | Unity 精确编辑器版本、包版本、渲染管线 |
| Node/Electron | `package.json`、锁文件、`.nvmrc` | Node 约束、Electron、构建器和依赖版本 |
| Tauri/Rust | `Cargo.toml`、`Cargo.lock`、`rust-toolchain.toml`、Tauri 配置 | Rust 工具链、Tauri 和 crate 版本 |
| Qt/C++ | `CMakeLists.txt`、`*.pro`、`vcpkg.json`、编译预设 | Qt、C++ 标准、编译器和依赖 |
| Java | `pom.xml`、`build.gradle*`、Gradle Wrapper | JDK、语言级别、JavaFX/Swing、构建工具 |
| Python | `pyproject.toml`、`.python-version`、锁文件 | Python、GUI 框架和依赖 |
| Go | `go.mod`、`go.sum` | Go 版本和模块依赖 |
| Flutter | `pubspec.yaml`、`.fvmrc` | Dart/Flutter 约束和包版本 |
| Swift | `Package.swift`、Xcode 配置 | Swift tools 版本、平台和依赖 |

依赖范围不等于精确锁定；需要锁文件或实际工具链复核。

## 4. 黑盒模式允许的非侵入性指纹

在授权范围内可记录：

- 可执行文件格式、CPU 架构和签名元数据；
- 随程序分发的公开运行库和动态库名称；
- 合法读取的进程、子进程和公开模块；
- .NET、JVM、Chromium、Qt、Unity 等明显运行时特征；
- 窗口类、可访问性控件树、WebView/原生控件表现；
- 资源目录、公开配置、日志、缓存和插件清单；
- 公开图形 API、媒体运行时、安装器和更新器行为。

不得进行进程注入、绕过保护、内存凭据提取、解密受保护资源或复制反编译源码。

## 5. `SOURCE_TECH_FINGERPRINT.yaml`

规范结构：

```yaml
schema_version: "1.1"
source_type: "black_box"
scan_root: "C:/Authorized/TargetApp"
scan_time: "2026-08-01T12:00:00+08:00"
status: "CONDITIONAL"

detected_facts:
  - fact: "检测到 Chromium 运行时文件"
    status: "OBSERVED"
    evidence_ids: ["EV-20260801-0001"]

candidates:
  - candidate_id: "SRC-TECH-0001"
    technology: "Electron"
    likely_language: "JavaScript/TypeScript"
    likely_framework: "Electron"
    exact_language_version: "UNKNOWN"
    exact_framework_version: "UNKNOWN"
    confidence: 0.82
    evidence_paths: ["resources/app.asar"]
    evidence_ids: ["EV-20260801-0001"]
    limitations:
      - "仅凭安装目录不能证明源代码语言版本"

runtime_and_binary_indicators: []
project_files_and_lock_files: []
unknowns:
  - "精确 Electron 版本尚未由直接证据确认"
notes: []
```

`status` 表示该指纹文档是否完成审查，不表示候选技术已被证明。黑盒项目可以在保留 `UNKNOWN` 和限制的情况下通过 G1-T。

## 6. 置信度建议

- `0.90–1.00`：源码、清单或锁文件直接确认，并与工具链复核一致；
- `0.70–0.89`：多个独立外部指纹一致；
- `0.40–0.69`：单一强指纹或多个弱指纹；
- `<0.40`：仅为待验证候选，不应用于目标架构决策。

置信度不是事实等级；黑盒证据再强，也不能伪装成已查看源码。

## 7. 应用拓扑

除语言外，还要识别：独立离线桌面、桌面客户端加本地服务、C/S 客户端加远程服务、Web UI 加桌面壳、插件宿主、设备控制端或混合拓扑。拓扑结论应来自进程、网络、配置、安装和断网测试，不得仅凭外观判断。

## 8. G1-T 通过条件

- 探测范围和授权已记录；
- 源码模式已检查主要清单、锁文件、构建脚本和 CI；
- 黑盒模式已明确精确版本不可确认的边界；
- 每个候选有证据、置信度和限制；
- 直接事实与推断分开；
- 所有未知项保持 `UNKNOWN`、`UNVERIFIED` 或 `BLOCKED`；
- 未将源技术候选直接当成目标技术决策。
